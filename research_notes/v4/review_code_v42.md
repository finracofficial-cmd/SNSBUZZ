## 問題がなかったところ（確認済み）

- **XSS**: 新しい `innerHTML` に入る値（お題の文・選択肢、週の名前は `WEEK_ID` を通した値だけ、グループの `handle`・`nick`、`confirmModal` の文、いまの二つ名、動画の `blob:` URL、プレゼントのページ）は `esc()` を通すか、形を確かめた値だけ。KPI 画面の新しい行も数値だけ。
- **CSP**: 動画の再生に `media-src 'self' blob:` を足してあり、`dist/_headers` にも入っている。インラインのスクリプトは増えていない。
- **D1**: SQL はすべてプレースホルダ。お題の集計は主キーの範囲（`poll:<週>:` 〜 `poll:<週>;`）。返金が購入より先に届いた場合・一部返金・申し立てに勝った場合はテストのとおり。グループの参加は `INSERT OR IGNORE`（同じ秘密で同時に押しても1行）。
- **週と時刻**: 2026年の1年分で、ブラウザ（`clock.js`）とサーバー（`week.js`）の週の名前が一致し、月曜0時（日本時間）で切りかわる。「次に変わるのは〇時」は、1年分を7分おきに総当たりして、実際に言葉が変わる時刻と全部一致した（深夜はカウントダウンなし）。
- **計算中の画面**: 書いてある3行（12問から4軸・16タイプから照合・隠しタイプ4種類の条件）は実際の計算どおり。待ち時間は案によらず同じ。動きを減らす設定の人には出さない。

  - `groupRoles` を DOM を使わない `logic.js` へ移し、「n 人なら min(n, 7) 個の役・同じ人に2つ付かない」をテストに足す。

### M1 おうちの人の完了画面が、1時間たつと「払っていない」に変わる

- 場所: `site/assets/app.js:189-200`（`viewBuyDone` は `childPaidAt` から1時間以内のときだけ「完了しました」、それ以外は「お支払いは完了していません…もう一度お手続きください」）、`site/assets/premium.js:517`（`childPaidAt` は支払いを受け取ったその時刻）

- 再現したか: 確認済み。`childPaidAt` を2時間前にして `#/buy/done` を開くと「お支払いは完了していません」と表示された。
- 直し方:
  - 完了の印は時間で消さない（`childPaid: { at, rid }` を残す）。
  - 印がないときの文は、払っていないと決めつけず「この画面では支払いの状態を確かめられません。お子さまのスマホで完全版が開いているかを確かめてください」にする。
  - できれば `GET /api/claim/status?rid=`（支払い済みかどうかだけを返し、トークンは返さない）を足し、`viewBuyDone` と `viewBuyFor` で「このお願いは支払い済みです」と出す。古いリンクを開き直したおうちの人の二重払いも防げる。

### M2 おうちの人へのリンクが、表示した日付より早く切れる

- 場所: `site/assets/premium.js:257`（リンクの作成日は `Math.floor(c.at / DAY)`＝**UTC の日**）、`premium.js:278-279`（おうちの人のページは「UTC 0時（日本時間9時）＋7日」を過ぎたら販売しない）、`premium.js:263`（画面の「〇月〇日まで有効」は `c.at + 7日` の日付）、`premium.js:248`（作成から6日以内なら同じリンクを出し直す）
- 何が起きるか:
  - リンクが実際に切れるのは「作成した日（UTC）の日本時間9時から7日後」。画面には「作成時刻＋7日の日付まで有効」と出る。日本時間0:00〜8:59に作ると、表示の**前の日の9時**で切れる（例：10/23 8:30 に作成 → 表示は「10/30まで有効」、実際は 10/29 9:00 で切れる。最大で約39時間早い）。9時以降に作っても、表示の日の9時で切れる（「〜まで」から読める、その日の終わりまでではない）。
  - 出し直しの条件（作成から6日以内）は作成時刻で見ているので、朝に作ったお願いを6日目の朝にもう一度出すと、残り数十分のリンクを「〇日まで有効」として送る。おうちの人が開くころには「このリンクの期限が切れています」になり、払えない。
- 再現したか: 確認済み（Chromium、Asia/Tokyo、時刻を固定）。
  - 10/23 8:30 に作成 → 表示「2026/10/30まで有効」。おうちの人が 10/29 8:50 に開くと購入画面、10/29 9:30 に開くと「このリンクの期限が切れています」。
  - 10/29 8:20 にお願いし直すと、同じ受け取りID・同じ作成日のリンク（表示はまた「10/30まで有効」）。9:05 に開くと期限切れ。
- 直し方:
  - リンクには作成時刻（時間単位、`Math.floor(c.at / 3600000).toString(36)` など）を入れ、判定も表示も `c.at + 7日` にそろえる。表示は「10/30 8:30まで」と時刻まで出す。
  - 出し直すのは残りが2日以上あるときだけにする。
  - サーバーの預かり（支払いから7日）と端末の確認期間（作成から14日）は、そのままでよい。

## 低

### L1 カード会社の「問い合わせ」で読めなくなり、閉じても戻らない

- 場所: `functions/api/stripe-webhook.js:59-66`
- 何が起きるか: Stripe では、カード会社からの問い合わせ（inquiry、`status: warning_needs_response`）も `charge.dispute.created` で届く。問い合わせはチャージバックではなく、返金なしの `warning_closed` で閉じることが多い。いまは `created` で止め、`closed` で戻すのは `won` のときだけなので、問い合わせが閉じたあとも、その購入（ふたり用ならプレゼントを受け取った友達も）はずっと読めない。払った人からの「読めなくなった」の問い合わせになる。
- 再現したか: 確認済み。SQLite で購入 → `charge.dispute.created`（`warning_needs_response`）→ 403 → `charge.dispute.closed`（`warning_closed`）→ 403 のまま。
- 直し方: `closed` で `status` が `won` か `warning_closed` なら戻す。または、`warning_` で始まる問い合わせでは止めず、本当の申し立て（`needs_response` など）になったとき（`charge.dispute.updated` も受ける）に止める。テストに問い合わせの流れを足す。

### L2 NGワード：許可語の消し方で悪口が通り、つなげて照合するせいで名前を弾く

- 場所: `functions/_lib/http.js:73-79`（空白・中黒・記号・のばし棒を消してから照合）、`http.js:87-91`（許可語を文字列から取り除いてから照合）
- 何が起きるか:
  - 許可語を消してから見るので、許可語に続けて書いた悪口が通る：「しねまじで」（「しねま」を消すと「じで」）、「きもちわるい」「キモチワルイ」（「きもち」を消す）、「ばかすみ」（「かすみ」を消す）。
  - 空白・中黒を消して語をつなげるので、2文字のNG語が名前の切れ目にできる：「ゆき もも」「まき もか」「みき・もえ」（きも）、「もも ころすけ」（ころす）。どれも v4 では通っていた名前で、新しく弾かれる。前からの「かすが」「たかすぎ」「あきもと」「ぼっちゃん」も弾いたまま。画面には「使えない言葉が入っています」しか出ないので、どこを直せばいいか分からない。
- 再現したか: 確認済み（`hasNgWord(cleanText(…))` を直接呼んだ）。
- 直し方:
  - 許可語は、文字列から消すのではなく「NG語が見つかった位置が許可語の範囲の中なら、その一致だけ無視する」形にする。
  - 2文字のNG語（きも・かす・しね・うざ・ぶす など）は、空白で区切った語の中だけで照合する。語をつなげて見るのは3文字以上のNG語だけにする。
  - 「きもちわるい」「きしょい」などを足す。どの言葉が引っかかったかを画面に出す（ブラウザでも同じ関数で確かめる）。

- 再現したか: していない（Chromium は `filter` に対応しているため）。要実機確認（iOS 17 以前の Safari と LINE の中のブラウザ）。
- 直し方: ぼかしを縮小→拡大で作る（カードを 36×64 程度に `drawImage` し、`imageSmoothingEnabled` のまま 720×1280 に引き伸ばす。2回くり返すと十分ぼける）。どのブラウザでも同じ見た目になる。`smoke.mjs` で、最初のフレームが結果カードと十分ちがうことを確かめる。

### L4 今週のお題：隠したタイプの票が引き算で分かる

### L5 いまの二つ名：カードが古いまま残る・祝日の抜け

- 場所: `site/assets/now.js:17-25`（`nowCard` は描いたときの言葉・時刻・「次に変わるのは」を HTML に固定）、`site/assets/app.js:96`（トップの「いまは〜」も同じ）、`site/assets/clock.js:39-44`（祝日）

### L6 A/Bテスト：あとから足した実験の表示を数えそこねる・calc の指標がない

- 場所: `site/assets/ab.js:16-20`（「送った」印は段階ごと `ab:sent:<段階>` で、実験ごとではない）、`site/assets/quiz.js:205-209`、`site/assets/admin.js`（A/B の表は 表示→購入案内→決済→支払い だけ）
- 何が起きるか:
  - すでに `exposure` を送った端末は、あとで足した実験の `exposure` を二度と送らない。一方、支払い（`paid`）は決済の目印（`abTag()`）で全部の端末ぶん数える。新しく足した実験は、両方の案で支払い率が実際より高く出て、z 検定の分母もずれる。いまは公開前で3つの実験が同時に始まるので影響はなく、次に実験を足したときに効く。
  - calc（結果の直前の「計算中」）は、効くとすれば「わかる〜！」の割合・シェア・くわしい診断へ進む率に効くはずだが、案ごとに数えているのはレポート表示からの購入の段階だけ。支払いは各案5,000人に届くまで判定しないので、calc はほぼ判定できないまま終わる。
- 再現したか: コードで確認。
- 直し方: 印を `ab:sent:<実験>:<段階>` にする。calc は `agree`・`share`・`detail:start` を案ごとにも数える（`event.js` の `ab` の段階に足す）か、判定に使う指標を先に決めて KPI 画面に出す。

### L7 確認画面がフォーカスを移さない（`window.confirm` からの置きかえ）

- 場所: `site/assets/ui.js:142-172`（`openModal`・`confirmModal`）、`site/assets/social.js:373-399`（抜ける・消す・外す）
- 何が起きるか: アプリの中のブラウザ対策として `window.confirm` を画面の中の確認（`confirmModal`）に置きかえたが、`openModal` はフォーカスを移さず、Esc でも閉じない。確認は `#app`（`aria-live`）の外、ページの最後の `#modal` に出るので読み上げられない。キーボードやスクリーンリーダーの利用者が「外す」を押しても確認に気づけず、フォーカスは後ろのボタンに残る。もう一度押すと確認が重なり、前の確認の Promise は解決されないまま残る。`window.confirm` は端末が確認にフォーカスを移していたので、この3か所では後退になる。
- 再現したか: コードで確認（`ui.js` にフォーカスの処理がない）。
- 直し方: `openModal` で `.sheet` に `tabindex="-1"` を付けて `focus()` し、閉じたら開いたときのボタンへ戻す。Esc で閉じる。開いているあいだ `#app` に `inert` を付ける。すべてのシートに効く。
