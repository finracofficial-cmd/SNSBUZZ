## 問題がなかったところ（確認済み）

- **Webhook の署名**: `t` と `v1` を取り出し、`${t}.${payload}` の HMAC-SHA256 を一定時間の比較で照合、5分の許容幅。記録は `INSERT OR IGNORE` なので、5分以内の再送が来ても数は増えない。ほかの商品の Session は `metadata.app/plan` で弾いている。
- **プレゼントの二重受け取り**: `UPDATE … SET gift_used_at = ? WHERE id = ? AND gift_used_at IS NULL` の変更行数で判定しており、同時に2人が受け取っても1人だけが通る。プレゼント券（`gift-`）では本文は読めない。
- **おうちの人の受け取り**: 子どもの端末だけが持つ130ビットの秘密 `s`、リンクにはその SHA-256 から作った80ビットの受け取りIDだけ。リンクが転送されても受け取れない。`s` が URL や共有文に出る経路はない。
- **価格と支払い方法**: 決済の前に Stripe の Price（`unit_amount`・`currency`・`active`）と画面の価格を照合し、ずれていれば販売しない。支払い方法は `card`・`paypay` だけに絞っている（v3 M2・M3）。
- **XSS**: 新しい `innerHTML`（`app.js:132` の実数、`result.js:127,206`、`social.js:126,400`、KPI 画面）に入る値は、`esc()` を通すか、サーバーが許可リストで作ったキー・数値だけ。ニックネーム・グループ名・URL の `f`・`n`・`me` の中身は、`cleanName`・`esc`・正規表現（`decodeResult` は先頭と末尾を固定）を通っている。抜けは見つからなかった。
- **オープンリダイレクト**: なし。移動先は Stripe が返した URL か、`/` + 自分のハッシュだけ（`returnHash` は `location.hash` から作る）。
- **CSP とキャッシュ**: `script-src 'self'` で、インラインのスクリプトはない（JSON-LD はデータブロックで実行されず、`<` も `<` にしている）。JS は1ファイルにまとめて中身のハッシュを名前に入れ、`immutable` で1年。HTML にはヘッダを付けていないので Pages の既定（毎回確かめる）になる。`/thanks/` は `no-store` と `no-referrer`。
- **D1**: SQL はすべてプレースホルダ。`/api/stats` は主キーの範囲で読む。グループには、かんたん診断の結果だけを保存し、読むときにも切っている（v3 M7）。
- **補足（要確認）**: Cloudflare Pages の `_headers` の `/thanks/*` が `/thanks/` そのものにも効くかは、デプロイ後に `curl -I 'https://…/thanks/?sid=x'` で確かめる。効いていなければ `/thanks/` の行を足す。

## 中

### M1 おうちの人が決済をキャンセルしても「お支払いが完了しました」と出る

- 場所: `site/assets/premium.js:198`（おうちの人の決済では、移る前に `returnHash` へ `'#/buy/done'` を入れる）、`premium.js:440-444`（`cancelPurchase` はそれをそのまま返す）、`app.js:275`、`app.js:180-184`（`viewBuyDone`）
- 何が起きるか: おうちの人が Stripe の画面で「戻る」（＝キャンセル）を押すと、`/thanks/?canceled=1` → `cancelPurchase()` が `'/#/buy/done'` を返し、「お支払いが完了しました。お子さまのスマホで、完全版が読めるようになりました」と表示する。実際には請求も `claims` の行もない。おうちの人は払ったつもりになり、お子さまの端末はいつまでも開かない。問い合わせ（「払ったのに届かない」）の原因になる。Chromium で、おうちの人のページ → 購入内容を確認 → キャンセルの戻り先、の順に動かし、この表示になることを確認した。
- 直し方:
  - `returnHash` には `#/buy/<rid>`（おうちの人のページ）を入れる。`completePurchase` で `res.forChild` のときだけ `#/buy/done` へ移す。
  - `viewBuyDone` は、`afterPurchase` か `premiumToken` がないときは「お支払いはまだ完了していません」と、購入ページへのリンクを出す。
  - `/thanks/?canceled=1` のテスト（おうちの人・本人の両方）を `smoke.mjs` に足す。

### M2 プレゼントのリンクを開いただけで受け取り、本人や購入済みの人でも使ってしまう

- 場所: `site/assets/app.js:253-263`（`#/gift/` を開いた時点で、確認なしに `POST /api/gift`）、`premium.js:309-317`（`acceptGift` はいまのトークンを上書き）、`premium.js:300-306`（`acceptToken` も同じ）、`functions/api/gift.js:21-37`（`Set-Cookie` で `pz_t` を上書き。`crossSite` の確認もない）
- 何が起きるか:
  1. ふたり用を買った人が、LINE に貼ったあと自分でリンクを押して確かめると、その場で受け取り済みになり、友達は「もう受け取られています」になる。友達の分（590円と390円の差）が消え、出し直しても `used` のまま。
  2. すでに自分で買った友達が開いても、同じように使われてしまう。
  3. 開いた人の `cs_` トークンは、localStorage と Cookie の両方で `gr-`（贈った人の購入）に置きかわる。あとで贈った人の購入が返金されると（18歳未満の返金）、自分でも払ったのに読めなくなり、Cookie からも戻せない。
  4. `POST /api/gift` は Origin を確かめないので、別のサイトのフォーム（`text/plain` で JSON の形を作る）から、閲覧者の Cookie を書きかえることもできる（影響は小さい）。
  
  Chromium で、購入済みの端末が `#/gift/…` を開くと POST が飛び、`premiumToken` が `gr-…` に置きかわることを確認した。
- 直し方:
  - `#/gift/` ではすぐに交換しない。「受け取る」ボタンを出し、押したときだけ交換する。`hasPremium()` のときは「もう完全版を持っています。このリンクは友達に送ってね」と出して交換しない。
  - サーバーでも、Authorization か Cookie のトークンが同じ購入（`cs_<id>` か `gr-cs_<id>`）なら `409 own` で断る。有効な `cs_` を持っている人も断る。
  - Cookie を書くときは、いま有効な `cs_` の Cookie を `gr-`・`promo-` で上書きしない（名前を分けるか、優先順位を付ける）。`gift.js` にも `crossSite` を入れる。
  - `acceptToken` も、いまのトークンが有効で別のものなら、置きかえる前に確認を出す。

### M3 memberId が全グループ共通で、管理者に全員分を返している（なりすまし・いやがらせ）

- 場所: `functions/api/groups/[id].js:32`（管理キーがあると全員の `member_id` を返す）、`[id].js:45-58`（`member_id` を知っていれば、その人のニックネームと結果を上書きできる）、`[id].js:83-85`（`member_id` だけで退出させられる）、`site/assets/social.js:329-330`（`memberId` は端末に1つで、どのグループでも同じ値）
- 何が起きるか: グループを作った人（たとえばクラスメイト）は、自分のグループの管理画面から、メンバー全員の memberId を取れる。memberId はほかのグループでも同じなので、作った人は、自分が管理者ではない別のグループでも、その子の名前を書きかえたり、抜けさせたりできる。自分のグループの中でも、「外す」ためだけの管理キーで、名前の書きかえ（なりすまし）までできる。スクラッチのテストで、グループ1の管理者が得た ID を使い、グループ2のメンバーの名前を「のっとり」に変え、DELETE で消せることを確認した。10代のグループ機能では、いやがらせに直結する。
- 直し方:
  - memberId をグループごとに作る（`memberId:<groupId>`）。
  - 本人だけが持つ秘密（`secret`）と、他人に見せる番号（`handle`。行ごとのランダム8文字など）を分ける。D1 には `secret` のハッシュを保存し、参加・更新・退出は `secret` で、管理者の「外す」は `handle` で行う。管理者にも `secret` は返さない。
  - いま保存されている行は、`handle` を振り直すだけで移せる（`secret` は既存の member_id のハッシュでよい）。

### M4 相性のおさそい・ふたりの相性のリンクに、くわしい診断のパラメータが入る

### M5 決済へ移る前に Session ID を残さないので、/thanks/ が開かなかった購入を受け取れない

- 場所: `functions/api/checkout.js:60-62`（Session の URL だけを返す）、`site/assets/premium.js:196-199`（そのまま Stripe へ移る）、`premium.js:414-416`（`pendingSid` を残すのは /thanks/ が開いたときだけ）
- 何が起きるか: 支払いのあとで /thanks/ が一度も開かなかったとき（PayPay のアプリに切りかわったあと元のブラウザに戻らない、アプリ内ブラウザが閉じた、通信が切れた、タブを閉じた）、購入した端末には sid が何も残らない。Webhook は購入を記録するが、ブラウザの側からそれにたどり着く手段がなく、`retryPendingPurchase` も動かない。v3 H1 の「戻れなかったら受け取れない」は、/thanks/ が開いた場合にだけ直っている。残る手段はメールでの問い合わせ（`issue-token.mjs`）だけ。PayPay のようにアプリを行き来する支払いでは、戻り先が OS の既定のブラウザ（Safari）で開くことがあり、LINE などのアプリ内ブラウザで始めた購入はこの形になりやすい。
- 直し方:
  - `checkout.js` で `{ url: session.url, id: session.id }` を返す。ブラウザは Stripe へ移る前に `pendingSid = { sid: res.id, at }` を保存し、`/thanks/?canceled=1` で消す。
  - `retryPendingPurchase` は、`unpaid`（402）なら残しておき、次に開いたときにまた確かめる。`boot()` だけでなく、`visibilitychange`（アプリから戻ってきたとき）でも1回確かめる。
  - /thanks/ に `returnHash` がない（＝別のブラウザで開いた）ときは、「購入したのと別のブラウザで開きました。元のアプリで読むには、この引き継ぎリンクを開いてね」を最初に出す。

### M6 引き継ぎリンクで開いた端末には Cookie が付かない。Cookie から戻すとプレゼントの入口が消える

- 場所: `site/assets/premium.js:300-306`（`acceptToken` は localStorage にだけ保存）、`premium.js:345`（コード欄に `v1.` を貼ったときも同じ）、`functions/api/premium/index.js:15-33`（`Set-Cookie` を返さない）、`scripts/issue-token.mjs:12`（サポートが送るのも `#/unlock/` のリンク）、`functions/api/restore.js:10`（トークンだけを返し、プランは返さない）、`premium.js:410` と `report.js:223`（プレゼントのボタンは localStorage の `plan` で出す）
- 何が起きるか:
  1. 引き継ぎリンクで開いた端末には Cookie が付かない。LINE の中で買い、引き継ぎリンクで Safari に移した人は、Safari 側には localStorage の記録しかないので、7日間開かないと（ITP）また読めなくなり、`/api/restore` でも戻らない。サポートで引き継ぎリンクを送り直した人（＝一度データが消えた人）も同じで、また消える。v3 H2 の対策（Cookie）が、いちばん必要な「別のブラウザへ移す」経路で効いていない。
  2. Cookie から戻したときは `plan` が戻らないので、ふたり用を買った人のレポートから「友達へのプレゼントのリンク」ボタンが消える。`GET /api/gift` はトークンだけで出せるのに、入口がなくなる。
- 直し方:
  - `POST /api/adopt` を作る（Authorization のトークンを `accessOf` で確かめ、`ok` なら `Set-Cookie`）。`acceptToken` の成功時に呼ぶ。または `/api/premium` で、Cookie がないか別のトークンのときに `Set-Cookie` を返す（M2 の優先順位に合わせる）。
  - `restore` は `SELECT plan FROM purchases` の `plan` も返し、ブラウザで保存する。`hasGift` は `GET /api/gift` の結果で決めてもよい。

## 低

### L1 返金の取りこぼし・一部返金・チャージバック

- 場所: `functions/api/stripe-webhook.js:45-47`、`functions/api/unlock.js:24-25`、`functions/_lib/purchase.js:208-226`
- 何が起きるか:
  - 返金は `UPDATE purchases SET refunded = 1 WHERE payment_intent = ?` だけ。行がまだないとき（`completed` の Webhook が失敗して再送待ち、Webhook を設定する前の購入）に返金すると何も残らず、そのあと24時間以内に /thanks/ の再試行で `/api/unlock` を呼ぶと、読めるトークンが出る。スクラッチのテストで、返金 → unlock が 200、`/api/premium` も 200 になることを確認した。
  - `charge.refunded` は一部返金でも届く。10円だけ返金しても、その購入（ふたり用ならプレゼントの相手も）が読めなくなる（確認済み）。
  - チャージバック（`charge.dispute.created`）は扱っていないので、不正利用の申し立てで返金されても読める。
- 直し方: `refunds(payment_intent PRIMARY KEY, at)` に必ず書き、`recordPurchase` と `accessOf` でも見る。止めるのは `obj.refunded === true`（全額）か `amount_refunded >= amount` のときだけにする。`charge.dispute.created` も止める対象に足す。

### L2 おうちの人の受け取り：期限の基準が端末とサーバーでちがう

- 場所: `site/assets/premium.js:215-219`（端末の期限は「リンクを作った時刻」から7日）、`premium.js:245-263`（おうちの人のページは期限を見ずに販売する）、`functions/api/claim.js:8,17`（サーバーの期限は「支払った時刻」から7日）
- 何が起きるか: 子どもがお願いして6日後におうちの人が払い、子どもが8日目に開くと、端末は受け取りIDを期限切れとして確かめに行かず、支払い済みなのに自動で開かない。8日目以降におうちの人が古いリンクから払った場合も、子どもの端末は秘密を新しいお願いで上書きしているので届かない。どちらも、おうちの人の端末の引き継ぎリンクで救えるが、画面では「自動で開きます」と案内している。
- 直し方: リンクに作成日を入れ（`#/buy/<rid>/<作成日>`）、`viewBuyFor` で7日を過ぎていたら「リンクの期限が切れています。お子さまにもう一度送ってもらってください」と出して販売しない。端末は、受け取るまで秘密を消さず、確かめる期限を「作成から14日」にする。

### L3 受け取り・再試行が終わると、診断の途中が消える

- 場所: `site/assets/premium.js:267-293`（`claimTimer` は画面を移っても最大15分動き、最後に登録したコールバックを呼ぶ）、`app.js:136`（ホームは `() => route()` を登録）、`app.js:326-331`（再試行が成功しても `route()`）、`app.js:210-213`（`route()` は `cancelQuiz()` する）
- 何が起きるか: 子どもがおうちの人にお願いしたあと、ホームから診断を始め、その途中でおうちの人の支払いが終わると、`route()` が呼ばれて診断が1問目からやり直しになる（途中の答えは保存していない）。
- 直し方: コールバックの中で、診断中（`session` がある）なら toast だけ出して描き直さない。描き直すのは、ホームかレポートを表示しているときだけにする。

### L4 続きリンク（#/me/）：型を確かめていない・LINE の中で開く

- 場所: `site/assets/carryover.js:32-33`（`code` に `data.q`・`data.d` をそのまま使う）、`result.js:363-371`、`result.js:87`（`done.code.startsWith`）、`result.js:353`
- 何が起きるか:
  - `decodeResult` は `String(code)` で確かめるので、`{"d":["f~1_1_1_1~6a4c28"]}` のように配列を入れた続きリンクも通り、`mineDetail.code` に配列が保存される。以後、かんたん診断の結果ページは TypeError で描けず、トップに戻される（Chromium で確認）。いたずらのリンクを1回開くと、くわしい診断をやり直すまで直らない。
  - 「LINE の Keep メモに送る」で送ったリンクは、LINE でタップすると、既定の設定では LINE の中のブラウザで開く。「LINE の中のブラウザと Safari のどちらでも続きから」という目的の、Safari 側へ移れない。
- 直し方: `typeof data.q === 'string'` を確かめ、保存するのは `encodeResult(quick)`（作り直した値）にする。LINE で外のブラウザが開くよう、`${ORIGIN}/?openExternalBrowser=1#/me/…` の形にする（引き継ぎリンクも同じ）。

### L5 わたしクイズの点数リンクが切れていると、点数が消える

- 場所: `site/assets/social.js:530`（ここだけ素の `decodeURIComponent`）、`app.js:246-249`
- 何が起きるか: LINE で途中が切れた `#/qs/%E3%81/6` を開くと、例外が `route()` の try/catch まで飛んでトップが出る。点数は記録されず、ハッシュも `#/qs/…` のまま残る（Chromium で確認）。
- 直し方: `safeDecode` を使い、名前が読めなくても「ななし」で点数を残す。`replaceState` は受け取りの成否にかかわらず行う。

### L6 NGワードの誤検出と素通り

- 場所: `functions/_lib/http.js:64-73`、`functions/api/groups/index.js:5-8`、`functions/api/groups/[id].js:8-11`
- 何が起きるか: 部分一致なので、「かすみ」「カスミ」「くずは」「きもち」「カステラ部」「ぼっち・ざ・ろっく」「殺せんせー推し」がすべて弾かれる（確認済み）。名前が「かすみ」の子は、本名でなくても自分の呼び名で参加できず、理由も表示されない。反対に、「馬鹿」「ﾊﾞｶ」（半角）「ば か」（空白）「ば​か」（ゼロ幅）「ＢＡＫＡ」（全角）「ブサイク」「死んで」は通る。制御文字は落としているが、ゼロ幅文字や文字の向きを変える文字（U+202E など）は残るので、名前の見た目を崩すこともできる。
- 直し方: 照合の前に、NFKC → カタカナをひらがなへ → 空白・ゼロ幅・向きの制御文字（`​-‏‪-‮⁦-⁩﻿`）を除く → 小文字、の順にそろえる。保存する名前からも向きの制御文字とゼロ幅文字を落とす。「かすみ」「くずは」「きもち」などの許可リストを足し、「馬鹿」などを足す。ブラウザでも同じ検査をして、どの言葉が使えないかを出す。

### L7 グループの運用面

- 場所: `site/assets/social.js:244`（管理キーは localStorage だけ）、`social.js:269`（管理キーをクエリに入れて送る）、`social.js:342,346,354`（`window.confirm`）、`functions/api/groups/[id].js:20-34`（GET に回数制限なし）、`[id].js:36-60`（外した人も、すぐ参加し直せる）
- 何が起きるか:
  - iPhone で作った人が7日間開かないと（ITP）管理キーが消え、荒らしを外すこともグループを消すこともできなくなる（グループは90日残る）。LINE の中で作ると、Safari では管理者にならない。
  - 外したメンバーは、同じ端末で「参加する」を押せばすぐ戻れる（新しい memberId でも可）。参加を締め切る手段がない。
  - `GET /api/groups/:id` に回数制限がない。ID は40ビットなので総当たりは重いが、当たればニックネームとタイプが読め、D1 の読み取りも使われる。
  - アプリ内ブラウザによっては `window.confirm` を出さずに false を返すものがある（要実機確認）。その場合「抜ける」「外す」「消す」を押しても何も起きない。
- 直し方: 作成時に「管理用リンク」（`#/g/<id>/a/<管理キー>`）を出して保存してもらう（引き継ぎリンクと同じ考え方）。`groups.locked`（参加を締め切る）を足す。GET にも回数制限をかける。確認は `openModal` の画面で行う。

### L8 有料とうたう「数値」と解説の前半が、無料側から読める

- 場所: `site/assets/radar.js:28` と `report.js:82`（モザイク中でも、レーダーの多角形は本当の数値で描く）、URL の `#/r/<コード>`（末尾6桁がそのまま数値）、`scripts/gen-content.mjs:42-53`（18通りすべての解説の前半を `types.js` に入れる）、`premium.js:94`（購入シートの1つめ「パラメータ6項目の数値と、くわしい解説」）
- 何が起きるか: 数値は、SVG の多角形の座標（0.1px 単位）と URL のコードから読める。解説は、18通りすべての前半（合計1,308字。有料のパラメータ解説3,255字の約4割）が公開の JS に入っている。URL のコードの6桁を書きかえて二つ名のもとになるパラメータを変えると、画面の「見本」にもほかの項目の前半が出るので、開発者ツールがなくても読める。
- 直し方: モザイク中のレーダーは、ランクの代表値（S=92・A=76・B=55・C=33・D=12 など）で描く。見本は有料文の一部ではなく、別に書いた短い文にする（または、見本を二つ名のパラメータの1文目だけにする）。購入シートの文言を実態に合わせる。

### L9 回数制限の書きこみ費用と、トップの「〇人が診断」

- 場所: `functions/_lib/http.js:33-37`、`functions/api/event.js:33-49`、`functions/api/stats.js:17-22`、`site/assets/app.js:46-55`、`quiz.js:187,191`
- 何が起きるか:
  - 回数制限そのものが、リクエストのたびに D1 へ1回書きこむ（はじかれたリクエストも）。`/api/event` は1回で4書きこみ、`/api/restore`（未購入でレポートを開くたび）も1書きこみになる。バズったとき、書きこみの量と費用が計測の分だけで大きくふくらむ。
  - `DELETE FROM rl WHERE exp < ?` は `exp` にインデックスがなく、表全体を読む（回数制限の呼び出し50回に1回）。
  - トップの「きょう〇人・これまで〇人が診断」は、人数ではなく完了の回数（同じ人が3回やれば3人）。回数制限は IPv6 の /64 ごとなので、/48 を持つ相手には6万5千倍に広がり、水増しもできる。表示は「人」なので、実際より多い人数を示すことになる。
  - `/api/stats?all=1`（KPI_TOKEN）にも回数制限がない。
- 直し方: `CREATE INDEX IF NOT EXISTS rl_exp ON rl (exp)` を足す。`/api/event` の回数制限は Cloudflare の Rate Limiting ルール（WAF）に移し、D1 には書かない。トップの数は、端末ごとに初めての完了だけを数えるキー（`first:done`）を足してそれを使うか、文言を「回」にする。`stats?all` にも回数制限をかける。

### L10 A/Bテストの数え方

- 場所: `site/assets/ab.js:5-13`、`premium.js:189-190`、`admin.js:92-94`
- 何が起きるか:
  - 案は localStorage に保存するので、iPhone で7日開かないと（ITP）振り直され、同じ人が両方の案を見たり、表示を2回数えたりする。
  - おうちの人の支払いには案の目印を付けないので、`paybar`・`autopay` の効果のうち「おうちの人にお願い」に流れた分は、支払い完了に数えない。
  - KPI 画面は、見るたびに p<0.05 なら「差がありそう」と出す。毎日見て、出たところで止めると、本当は差がなくても、5%よりずっと高い確率で「差あり」と判断してしまう。
- 直し方: おうちの人へのリンクに子どもの端末の案（`abTag()`）を付け、その決済の `metadata[ab]` に入れる。判断は、先に決めた人数（各案の必要数）に達したときだけ出す、と画面に書き、それまでは p 値を出さない。

### L11 iOS：共有シートが出ないことがある・キャンバスを解放しない（要実機確認）

- 場所: `site/assets/result.js:103-111,208-218`、`report.js:257-275`、`ui.js:222-235,261-275`、`carousel.js:329-339`
- 何が起きるか: 画像（6枚なら 1080×1920 を6枚）を作り終えてから `navigator.share` を呼ぶので、作るのに時間がかかると、Safari ではボタンを押した扱いが切れて `NotAllowedError` になり、共有シートではなく「長押しで保存」の画面になる（代わりの画面があるので壊れはしない）。`0334b40` の動画（録画に6秒かかる）では、ほぼ毎回この形になるはず。6枚の画像は約50MBのキャンバスを使い、使い終わっても解放しない。続けて何度か押すと、古い iPhone ではキャンバスのメモリの上限に当たり、真っ白な画像や `toBlob` の null になる。
- 直し方: 作り終えたら「共有する」ボタンを出し、そのボタンを押したときに `share` する（2段階）。`toBlob` のあとで `canvas.width = canvas.height = 0` にして解放する。

### L12 本番のドメインを設定しないままだと、特商法の表記が仮でも販売が始まる

- 場所: `scripts/build.mjs:168-174`、`functions/_lib/token.js:142`
- 何が起きるか: ビルドを止めるのは `SITE.origin` が example.com 以外のときだけ。`ORIGIN` は example.com のときに `location.origin` へ切りかわるので、`*.pages.dev` などに origin を変えずに出しても、シェアも決済も動く。この状態で Stripe の環境変数を入れると、「（販売事業者名）」「（メールアドレス）」のまま販売が始まる（警告は出るがビルドは通る）。
- 直し方: サーバー側の `premiumEnabled` で `env.SELLER_READY === '1'` も必須にする（v3 L5 の案）。または、販売者情報を config.js ではなく環境変数から `/api/premium/status` で返し、空なら販売しない。

## 優先順位（直す順）

1. **M1**（キャンセルで「完了」と出る）と **M2**（プレゼントがその場で消える）。どちらも利用者がふつうに踏む操作で、直すのは数行。
2. **M3**（memberId の流用）と **M4**（パラメータがリンクに入る）。10代のグループと、恋愛まわりの結果の公開にかかわる。
3. **M5**・**M6**（受け取れない・また消える）。v3 H1・H2 の残り。checkout が Session ID を返すことと、Cookie を付ける API を1つ足すことで、ほぼ片づく。
4. L1（返金）・L2（受け取りの期限）・L12（特商法）。販売を始める前に。
5. L6・L7（グループの安全）、L3〜L5（画面の不具合）、L8〜L11（計測・見せ方・iOS）。
